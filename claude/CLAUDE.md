# General working rules (all projects)

- Reply to the user in Turkish; keep status messages short.
- Plan: Claude **Max 20x** (stated by the user 2026-10-11; `get_usage` just says "Max"). Sessions, subagents and scheduled tasks share the 5-hour and weekly limits. Check `get_usage` before a large fan-out.
- Memory and vault notes are snapshots. Verify live state (server, repo, version) before acting on or asserting them.
- Session title (desktop app): keep it current with `mcp__ccd_session_mgmt__set_session_title` (session_id "self"). Format `<proje>: <konu>`, Turkish, short. In the ZZ root (no project folder) the prefix is the topic, not "ZZ": `sistem:` (Claude Code, orkestra, kurulum, hesap/araç ayarları), `araştırma:` (dış repo ve fikir incelemeleri), `marka:`, `kişisel:`; work that belongs to a project keeps that project's name (`tussle:`, `pano:`, `ziroo-edge:`…). Set it once the task is clear and update it whenever the topic shifts (no need to ask; it is one cheap call). Don't rename on every small step.

## Orchestration
- Sizable multi-step work: the main chat is the coordinator. It plans, asks the user for product decisions, delegates to background subagents (`run_in_background: true`), then reviews, tests and commits. Agents edit the working copy in place and don't commit; use `isolation: "worktree"` (own branch) only when parallel agents could touch overlapping files or the work is risky or experimental. This is a standing permission; don't ask per task.
- Side sessions (`start_session`, desktop app) vs subagents: a subagent stays the default for mechanical, review, discovery and single-slice work (cheapest, invisible to the user). Use a side session instead when (a) project work comes up in the ZZ root session: start it directly in the project's folder (`preset` or `cwd`, from `list_start_targets`) with the handoff note as the brief, instead of writing the note to the vault and waiting for the user to open a session; (b) the work will run for hours or the user will want to watch and steer it; (c) it is a self-contained next task better started fresh than from a long history. `context: "fork"` only while this conversation is short; otherwise `"fresh"` with a full brief. A proposal card (`own_initiative`) always opens in the current folder and cannot carry `preset`/`cwd`, so never propose project work from the ZZ root as a card: say in one line that it belongs in the project's session and start it with `user_asked` + `preset` once the user says go (learned 2026-10-15: the Tussle backup session opened in ZZ instead of mobil-playus). Workflows and cloud sessions only when the user asks; no cloud environment is set up (2026-10-15).
- Inline vs agent: an agent starts cold (~45–50k tokens of context). Go inline for short work with little reading (one-line fix, config or memory edit, git/deploy steps, quick check). Delegate when it needs a lot of reading or editing, even if the change is small, and whenever the coordinator's context is getting large.
- Split by feature (vertical slice), not by role. Parallel agents only on areas that don't overlap.
- Agent size: cost is context × calls, not agent count (each call re-reads the whole context; at 400k+ a call costs ~3x one under 200k), and very long contexts also lower quality. The primary cap is ≤200k context per agent. Call count is a signal, not a hard stop: around 100 calls, split at the next natural phase boundary (a fresh agent with a short handoff note: files, decisions, hypotheses, what's left); a debugging agent close to the root cause may finish first rather than lose its hypotheses mid-investigation. Plan work that would take 150+ calls as phases from the start. Don't split small work; a cold start is cheap. The `ajan-tavani.mjs` PostToolUse hook reminds the agent itself at 200k context, every ~40 calls past 100, and every 5 screenshots; the coordinator no longer needs to repeat these caps in every brief, but a brief for work expected to exceed them still says where the phase boundary is.
- Repeated same-pattern work (e.g. several themes): one agent builds the first instance plus the shared seam and lists the files involved; the rest get that exact spec. Mechanical repeats may go to `sonnet`; design and feel stay on `opus`.
- Every agent prompt includes the lean-context rule: if the project has a code map (`docs/kod-haritasi.md` or wherever its CLAUDE.md points), read it first and search from there; read a file of up to ~500 lines whole in one call (cheaper than several slices, since every extra call re-reads the whole context, and the agent sees the full picture); read only line ranges of larger files, guided by the map or a grep; don't re-read files already read; pipe build/test/install output through `grep -iE "error|fail|warn"` first, then `tail -40`, never the full log. Browser checks, in agents **and in the coordinator alike**: prefer `read_page` / `get_page_text` / `javascript_tool` over screenshots; a screenshot only when layout itself is the question, at `scale: 0.5`, and at the end rather than after every step (each image stays in context and is re-read on every later call). A coordinator that needs more than a handful of browser steps delegates the whole browser pass to an agent instead of driving it itself (learned 2026-10-16: one coordinator session took 135 screenshots and reached 628k context, 62 $ in a day).
- Discovery before code: when a task needs "find where X lives / which files touch Y", run that first as the `kesif` agent type (`~/.claude/agents/kesif.md`: Haiku, read-only, reads the code map first, returns file:line lists) or a few greps inline and put the resulting file:line list in the Opus agent's brief, so the Opus agent starts editing instead of searching.
- Code map: every project with real code gets `docs/kod-haritasi.md` via the global `kod-haritasi` skill (template, rules, and `~/.claude/skills/kod-haritasi/harita.mjs iskelet|kontrol`). Before a commit that adds, deletes or moves files or changes an area's entry point, the coordinator runs `harita.mjs kontrol` and fixes the map in the same commit. A project without a map: offer to create one when starting sizable work there.
- Coordinator: rely on the review agent's findings instead of reading whole agent diffs; past ~300k context, save decisions to the vault and `/compact` or hand off to a fresh session (the `baglam-uyarisi.mjs` UserPromptSubmit hook adds a reminder above 300k and when an old session is reopened above 150k; when it fires, tell the user in one line). Check `get_usage` context when a session passes ~2 hours or ~100 calls. Don't resume an old session whose context is already above ~150k for new work; start a fresh session with a short brief (reopened 7 Oct sessions cost 7–11 $ for a few dozen calls on 15–16 Oct).
- Agents never commit to main, merge, tag, release, deploy, touch secrets or SSH into production (scheduled read-only routines, such as Diskort's watcher, may read production over SSH). The coordinator does those within the project's rules.
- Models: the user picks the coordinator's model and effort per session (Fable or Opus; since 19 Oct mostly Opus); subagents never inherit it. Default `model: "opus"` with `effort: "medium"` (raise to `"high"` for cross-cutting or design-heavy work and deep reviews); `sonnet` for narrow well-specified changes, verifier/skeptic passes and tooling; `haiku` (`kesif`) or Explore for read-only search, file discovery, log/test-output summaries and pre-publish reads of internal text; outward-facing text (store listings, brand copy, public pages) gets `sonnet`. Always pass `model` explicitly.
- Relay agent results concisely; never present unverified agent claims as verified. Clean up any worktrees and branches after merging.

## Review gate
- Agent types (`~/.claude/agents/`): `inceleme` (review, opus medium) and `supheci` (skeptic, sonnet) carry the read-only rules, scope and output format below; the brief only names the diff (base/target), the area, and whether it is a risky area (then pass `effort: "high"`).
- Before committing or merging agent code changes (a branch or the working-tree diff), a separate read-only review agent (`inceleme`, not the author) checks the diff for security and correctness bugs, with verified file:line findings. Tell review agents to stay read-only: `git diff` / `git show`, no checkout and no changes to the main working copy. Scope the review to the diff: the diff plus ~40 lines around each hunk and the direct callers of changed functions; no whole-file or whole-repo reads; aim for ≤30 tool calls and ≤120k context. Exception: diffs touching auth/sign-in, payments/IAP, server or API code, permissions, secrets handling or data migrations get `effort: "high"`, may follow callers beyond the direct ones, and have no call cap (still ≤200k context).
- Non-code work (memory, vault, docs, settings): no review agent. The coordinator re-reads the changed files and checks links and secrets itself, and never trusts the agent's report alone.
- Medium-or-higher findings: a skeptic agent (`supheci`, sonnet) tries to refute each against the code (CONFIRMED / REFUTED / DOWNGRADE) and judges the proposed fix. The coordinator decides and reports disagreements. No findings, no skeptic.
- Fix high and critical findings before merging.

## Decision split
- The user decides: what to build and its priorities; releases, deploys and irreversible or outward-facing actions; budget, security boundaries and product feel.
- Claude decides how (agent split, models, testing, code structure) and briefly reports what it chose.

## Server (VPS)
- Always reach the VPS as `ssh vps '...'` / `scp <file> vps:<path>` (alias in `~/.ssh/config`: key, root, timeout; allow rules `Bash(ssh vps *)`, `Bash(scp * vps:*)`, `Bash(scp vps:* *)`, since 2026-10-15). Never spell out `-i`/`-o` flags or the IP. Put an ssh/scp call alone in its own Bash call, not chained with local commands (`cd … && ssh …`, `find … ; ssh …`): a compound command must match a rule in every part, otherwise the auto-mode classifier blocks it.

- After a substantial session, or when asked, write decisions (with why + rejected alternatives) and lessons there, following `~/ZZ/brain/CLAUDE.md`. Never write secrets into it.
